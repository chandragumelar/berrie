# Fondasi aplikasi Berrie

## Pembayaran tunai batch pertama (internal)

`payConfirmedFirstBatchCash(db, {orderId, expectedBatchRevision, expectedSessionRevision, received}, metadata)` mencatat uang yang benar-benar diterima untuk seluruh unit batch pertama confirmed, baik belum, sebagian, maupun seluruhnya disajikan. Jumlah harus positif dan `received` integer rupiah aman minimal tagihan; kembalian adalah selisih, dan ledger `sale` menambah kas sebesar tagihan. Pembayaran langsung untuk order platform juga memakai Payment biasa; tagihan platform tidak dibuat. API ini tidak menangani draft belum confirmed; jalur tunai draft dijelaskan di bawah. Jalur Rp0 internal dijelaskan di bawah; batch tambahan dan metode lain belum ditangani.

Command menyalin intent sebelum Web Lock, memeriksa receipt dahulu, lalu membaca ulang batch, sesi, revisi dan histori di transaksi IndexedDB. Snapshot harga, promo dan tarif berasal dari batch; kalkulasi serta alokasi menggunakan domain bersama. Settlement, Payment, penerimaan penjualan, job pelanggan berisi snapshot batch/settlement/payment, audit, outbox, receipt dan sequence disimpan atomik. Sesi direvisi agar seluruh pergerakan kas terurut. Stok, batch, job dapur dan penyajian tidak berubah. Retry harus memakai input dan metadata identik; operation ID sama dengan intent berbeda ditolak. Tidak ada jaringan atau cetak dalam transaksi; job bukan bukti kertas keluar.

Record dan receipt lama serta generik tetap memakai kontraknya; validasi histori baru mengikat batch, settlement, payment, job dan ledger serta menolak settlement draft yang tidak melalui jalur ini. Checkpoint/staging memeriksa hubungan tersebut, tetapi bukan autentikasi atau restore produksi. API dan pembacaan saldo hanya internal: `actorId`/`policyVersion` bukan otorisasi; T-04 harus memverifikasi identitas, izin, perangkat dan sesi sebelum integrasi UI. Belum ada auth/permit, serah-terima kas, sync, transport printer atau deployment; non-tunai, refund served dan tutup kas internal dijelaskan di bawah. Tes lokal memberi bukti parsial AC-10/20/22/24/30/39/48/151, bukan kelulusan AC operasional, T-10 atau pilot.

## Konfirmasi batch pertama (internal)

`confirmFirstBatch` menerima ID draft, revisi draft serta revisi mapping dan saldo grup yang diperoleh dari `planStoredDraftStock`. Intent disalin sebelum Web Lock; di dalam transaksi command membaca ulang seluruh sumber dan menolak revisi, saldo, toko atau referensi yang berubah. Semua unit fisik, termasuk unit gratis, didebit sekali per grup. Batch nomor 1 menyimpan snapshot draft dan pemetaan grup; satu job dapur persisten berisi snapshot yang sama. Batch, job, saldo, ledger, audit, outbox, receipt dan sequence disimpan atomik. Retry intent identik dengan operation ID sama mengembalikan hasil awal; ID yang dipakai untuk intent berbeda ditolak. Draft yang sudah dikonfirmasi tidak dapat diedit, dibaca atau direncanakan sebagai draft aktif.

Validator record dan histori memeriksa hubungan sumber draft, mapping, batch, debit dan job pada commit dan staging; data generik lama tidak diasumsikan sebagai record baru. Ini API internal tanpa UI dan tanpa pengiriman printer. `actorId` dan `policyVersion` bukan bukti izin: autentikasi, permit, validasi katalog dan izin sesi operasional tetap prasyarat integrasi. Job persisten bukan bukti cetak fisik; staging bukan restore produksi.

Scaffold belum dapat digunakan untuk transaksi. UI dan data contoh tetap di `../berrie-site/`; integrasi UI mengikuti T-06 setelah fondasi dan izin siap.

Dengan Node 22 dan npm: `npm ci --legacy-peer-deps`, `npm run dev`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. `npm run test:browser` menjalankan tes Chrome lokal melalui Playwright; konfigurasi saat ini memakai Chrome di `/Applications/Google Chrome.app`. `.env.example` tidak berisi rahasia. Lockfile mencatat versi terpasang.

`src/domain` mencakup kalkulasi dan snapshot awal, `src/storage` berisi primitive Dexie berversi, pemeriksaan revisi/urutan dan Web Locks. Ini belum merupakan API transaksi berizin: T-04 harus memvalidasi identitas, kebijakan, permit dan perangkat aktif, dan command bisnis harus memvalidasi seluruh invariants dalam transaksi. Web Locks yang tidak tersedia menyebabkan penolakan, bukan fallback tanpa lock. Checkpoint/staging awal bukan backup terenkripsi atau restore produksi; tidak mengaktifkan database staging. Lihat tasks untuk pekerjaan dan batas yang tersisa.

`stageSnapshot(db, input)` menerima `unknown`, memvalidasi checkpoint schema 1 dan hubungan receipt/state/event/sequence sebelum menulis atomik ke database staging yang masih kosong. Fungsi tidak mengaktifkan staging atau mengubah database sumber. Nilai state baru dapat menggunakan envelope `{ recordType: 'settlement', schemaVersion: 1, settlement }` atau `{ recordType: 'refund-history', schemaVersion: 1, settlement, refunds }`. Gunakan `createSettlementRecord` dan `createRefundHistoryRecord` di `src/domain/business-record.ts`; keduanya memvalidasi dan menyalin input. Commit memvalidasi nilai bertanda sebelum menulis; checkpoint/staging memvalidasi state terkini dan setiap nilai state dalam payload receipt historis. Penanda/versi yang tidak dikenal ditolak. Record generik lama tanpa `recordType` tetap diterima dengan kontrak storage lama, termasuk objek dengan `kind`; isi bisnisnya belum divalidasi. Tidak ada penebakan tipe atau migrasi data lama. Validasi konsistensi bukan bukti autentisitas, otorisasi, atau perlindungan dari manipulasi checkpoint yang terkoordinasi.

`planStockDebits(input)` di `src/domain/stock.ts` menerima `unknown`: `{ rows: [{ rowId, skuId, groupId, qty }], balances: [{ groupId, balance }] }`. ID baris dan grup saldo harus unik dan tidak kosong; SKU boleh berulang. Qty integer 1–999, saldo integer aman ≥0, dan setiap grup baris harus tersedia. Input tidak sah atau overflow melempar error; daftar kosong menghasilkan rencana kosong. Hasil sukses mengurutkan grup dan sumber berdasarkan ID serta memuat kebutuhan, saldo sebelum/sesudah dan sumber; kekurangan menghasilkan `{ ok: false, shortages }` tanpa debit parsial. Contoh dua baris rasa berbeda masing-masing qty1 dalam grup saldo50 menghasilkan kebutuhan2 dan sisa48. Qty mencakup unit gratis/promo; tidak ada konversi, resep atau stok topping.

Ini hanya perhitungan calon konfirmasi, tidak mengubah saldo. Pemanggil kelak wajib memilih hanya unit draft yang belum confirmed dan memvalidasi ulang saldo serta revisi dalam transaksi atomik bersama efek bisnis lain. Fungsi ini tidak membuktikan debit aktual, idempotensi, retry atau integrasi storage.

`planDraftStockDebits(input)` di `src/domain/draft-stock.ts` menerima `unknown`: `{ draft, skuGroups: [{ skuId, groupId }], balances: [{ groupId, balance }] }`. Draft divalidasi dengan `validateDraft`; tiap SKU harus memiliki tepat satu mapping tidak kosong, dan tiap grup yang dipakai harus memiliki saldo. Mapping duplikat, saldo duplikat/hilang atau input tidak sah ditolak. Setiap baris memakai ID item, SKU, grup dan panjang `unitIds`; seluruh unit fisik termasuk gratis/promo dihitung, sedangkan pilihan/topping tidak menambah debit. Agregasi, pemeriksaan saldo, urutan dan hasil `StockPlanResult` didelegasikan ke `planStockDebits`; kekurangan tidak menghasilkan rencana parsial. Contoh qty200 dari saldo1000 menyisakan800, dan dua SKU qty1 dari saldo50 menyisakan48. Input dan hasil terisolasi; fungsi tidak menulis database atau saldo.

Adapter hanya berlaku untuk model draft tersimpan yang belum pernah dikonfirmasi, bukan order campuran confirmed/draft. Mapping dan saldo diberikan pemanggil dan bukan bukti izin atau ketersediaan katalog. Command konfirmasi internal membaca dan memvalidasi ulang mapping, saldo dan revisi dalam transaksi; rencana ini sendiri bukan debit atau konfirmasi. Tes integrasi create/read memeriksa checkpoint seluruh koleksi tetap identik setelah sukses, kekurangan dan input gagal, tanpa ledger baru. Ini bukti parsial AC-123/151, bukan kelulusan operasional.

## Command draft lokal internal

`createDraft(db, data, metadata)` menyimpan order yang belum pernah dikonfirmasi; `updateDraft(db, data, metadata, expectedRevision)` mengganti draft tersimpan; `readDraft(db, orderId)` mengembalikan draft dan revisinya atau `undefined`. Ini bukan API operasional berizin: `actorId` dan `policyVersion` bukan bukti identitas atau izin, dan command tidak boleh dihubungkan ke UI sebelum T-04 memverifikasi izin, perangkat dan sesi. Command memeriksa sesi kas asal yang ada dan setoko; belum memvalidasi katalog, ketersediaan stok, atau izin penjualan.

Data draft berisi UUID order, sesi kas, baris, SKU, unit, pilihan dan topping; identitas antrean/nama, channel, penyajian, catatan, kutipan harga/promo/tarif, dan opsional order asal. Pilihan/topping menyimpan ID dan nama, topping juga harga; `toppingPrice` harus sama dengan jumlah harga topping. Kuantitas adalah panjang `unitIds` per baris (1–999). Draft kosong ditolak saat create maupun update; menghapus seluruh unit melalui lifecycle pembatalan belum dicakup. Harga dan total dihitung domain bersama; tidak ada snapshot settlement, batch, ledger stok/uang atau cetakan yang dibuat.

Saat create, nomor dan `savedAt` dalam data diabaikan: metadata menyediakan `recordedAt` UTC sebagai waktu kejadian dan `storeTimeZone` IANA. Setelah lock diperoleh, command membaca jam perangkat untuk `savedAt` dan waktu pencatatan audit, lalu mengalokasikan nomor per tanggal toko dan epoch dari histori draft bertipe. Pemanggil bertanggung jawab menggunakan waktu kejadian/zona yang benar; sumber waktu tepercaya dan otorisasi belum tersedia. Update memakai UUID, nomor, sesi dan revisi asal dari hasil read; `savedAt` diisi ulang dari jam perangkat saat commit. Baris/unit yang tetap ada mempertahankan ID; ID yang sudah dihapus tidak dipakai ulang. ID eksternal platform ditrim dan diperiksa unik dalam histori draft bertipe per toko/channel/akun. Record generik lama tetap diterima tanpa ditebak menjadi order: nomor atau ID platform tersembunyi di dalamnya tidak dapat direkonsiliasi otomatis; integrasi/migrasi mendatang harus menyelesaikan data tersebut sebelum penggunaan operasional.

Metadata juga berisi `operationId`, `storeId`, `deviceId`, `deviceEpoch`, `localSequence`, `actorId` dan `policyVersion`. Simpan dan gunakan ulang seluruh input serta metadata yang sama saat hasil tidak diketahui: retry identik mengembalikan hasil asal, perubahan apa pun dengan operation ID sama ditolak. Update bersaing pada revisi yang sama menghasilkan satu sukses dan satu konflik. Data disalin sebelum menunggu Web Lock; revisi, tipe target, nomor, audit sebelum/sesudah, state, outbox, receipt dan sequence diperiksa/ditulis atomik. Tidak ada efek jaringan atau printer dalam transaksi.

Envelope `{recordType:'draft', schemaVersion:2, draft}` untuk penulisan baru divalidasi pada commit dan pada setiap state serta receipt checkpoint; staging yang gagal tidak mengubah sumber atau meninggalkan sebagian data. Validasi histori menolak duplikasi identitas dan penggunaan ulang ID yang telah dihapus. Ini belum mengaktifkan staging/restore atau membuktikan otorisasi; jalur settlement internal dijelaskan di bawah.

## Sesi asal dan penyajian batch pertama (internal)

Create/update draft dan `confirmFirstBatch` membaca ulang sesi asal setelah Web Lock, di dalam transaksi. Sesi harus ada dan setoko; update memakai identitas sesi dari draft asal dan menolak penggantian. Sesi yang sedang dihitung atau telah ditutup menolak mutasi baru; receipt intent identik tetap dapat di-replay. Tidak ada sesi yang dibuat atau dipindahkan secara otomatis. Penyimpanan draft tetap tanpa debit stok; konfirmasi tetap mendebit sekali.

`readServing(db, storeId, orderId)` mengembalikan state unit batch pertama dan revisi (`null` sebelum operasi pertama). `serveUnits` dan `correctServing` menerima `{orderId, expectedRevision, unitIds, reason}` beserta metadata operasi. Untuk menyajikan, `reason` harus `null`; untuk koreksi wajib teks beralasan. Pilih semua unit dengan status `processed` dari hasil baca untuk menyajikan seluruh sisa. Pilihan kosong, duplikat, asing, belum confirmed, status salah, revisi basi, sesi atau toko salah ditolak. State unit `processed`/`served`/`cancelled` disimpan terpisah dari snapshot batch dan job dapur immutable; audit menyimpan sebelum/sesudah dan alasan. Seluruh unit served tidak berarti lunas atau pesanan selesai. Tidak ada perubahan stok, ledger uang, settlement, harga, pembayaran atau job cetak pada kedua operasi.

Simpan input dan metadata persis untuk retry: receipt diperiksa sebelum guard state terkini; ID yang sama dengan intent lain ditolak. Input disalin sebelum menunggu lock; state, audit, outbox, receipt dan sequence ditulis atomik. Checkpoint schema 1 tetap dipakai. Draft, batch dan job baru memakai record versi 2 dan receipt kontrak 2 berisi ID/revisi sesi sumber; histori memeriksa revisi tersebut dan urutannya. State penyajian memakai record/kontrak versi 1 dan divalidasi terhadap batch serta state penyajian pada revisi operasi, bukan hanya state terakhir. Record dan receipt versi 1 lama tetap divalidasi sesuai kontrak lamanya, termasuk yang tidak memiliki sesi valid; replay lama tetap tersedia, tetapi mutasi baru ditolak bila sesi asal tidak ditemukan atau berbeda toko. Record generik tetap tidak ditebak. Penanda versi bukan autentikasi checkpoint, dan validasi tidak melindungi dari seluruh manipulasi terkoordinasi.

Semua API ini internal, tanpa koneksi UI: T-04 harus memverifikasi identitas, izin dan approval koreksi; `actorId`/`policyVersion` bukan bukti izin. Pembayaran tunai batch pertama tersedia secara internal seperti dijelaskan di atas; batch tambahan, penutupan/serah-terima kas, server/sync, printer fisik dan restore produksi belum ada; refund served internal dijelaskan di bawah. Pengujian lokal hanya bukti parsial AC-17/39/48 dan regresi AC-09/20/151, bukan kelulusan AC atau pilot.

## Fondasi grup stok internal

`createStockGroup(db, {groupId, balance, minimum?}, metadata)` membuka satu grup dengan saldo eksplisit termasuk nol dan tepat satu ledger opening; minimum default 5. `readStockGroup(db, storeId, groupId)` membaca saldo dan revisi. `correctStockBaseline(db, {groupId, value, reason, expectedRevision, expectedBalance}, metadata)` menetapkan baseline dan saldo ke hitungan aktual, dengan delta dari saldo sebelumnya; alasan wajib. `setStockMinimum` memakai input yang sama tanpa alasan, dan hanya mengubah minimum tanpa ledger. Angka integer aman nonnegatif; identitas grup dan toko tetap. Metadata memuat operationId, storeId, deviceId, deviceEpoch, localSequence, actorId, policyVersion dan recordedAt UTC. Simpan input dan metadata yang sama untuk retry hasil tak diketahui; ID operasi sama dengan intent berbeda ditolak. Input disalin sebelum lock, dan state dibaca ulang dalam transaksi bersama ledger, audit, outbox, receipt dan sequence. Revisi atau saldo basi dan identitas lintas toko ditolak.

Envelope `stock-group` versi 1 divalidasi pada commit dan checkpoint; histori dan ledger opening/koreksi serta audit diperiksa bersama pada checkpoint/staging. Record generik lama tidak ditebak atau dimigrasikan. Staging bukan aktivasi restore, dan validasi konsistensi bukan autentisitas. Command hanya internal: actorId bukan bukti izin; jangan hubungkan UI sebelum T-04. Belum ada katalog, stok masuk, sinkronisasi atau pemulihan produksi; mapping, debit batch pertama dan return refund served internal dijelaskan di bagian lain.

### Mapping SKU dan rencana stok draft internal

`registerSkuStockMapping` mendaftarkan satu grup stok yang sudah ada untuk pasangan toko/SKU; `readSkuStockMapping` membaca hasil dan revisinya. Mapping tetap, tidak membuat opening, tidak mengubah saldo dan tidak menulis ledger. Command menyalin intent sebelum Web Lock, memeriksa referensi dan keunikan di transaksi yang sama dengan state, audit, outbox, receipt dan sequence. Retry identik mengembalikan receipt asal; operation ID dengan intent berbeda ditolak. Record generik lama tidak diubah atau ditebak.

`planStoredDraftStock(db, storeId, orderId)` membaca draft, mapping dan saldo dalam satu transaksi baca IndexedDB, lalu mengembalikan rencana serta revisi sumber. Semua unit termasuk gratis dihitung; topping dan pilihan tidak menambah debit. Hasil bukan reservasi atau izin konfirmasi: command konfirmasi internal membaca ulang dan memvalidasi seluruh sumber dalam transaksi tulis. API ini internal, belum terhubung UI atau otorisasi T-04; actorId dan policyVersion bukan bukti izin. Validasi checkpoint/staging memeriksa histori mapping, tetapi bukan autentikasi data atau aktivasi restore.

### Fondasi sesi kas lokal (internal)

`storage/cash-sessions.ts` menyediakan `openCashSession`, `moveCash`, dan `readCashBalance`. Pembukaan menerima UUID sesi, nomor, penanggung jawab awal, modal integer dan zona toko; metadata membawa toko, actor, waktu, operation ID, epoch dan sequence. Tanggal bisnis disnapshot saat pembukaan. Pergerakan menerima sesi, revisi yang diharapkan, arah, nominal positif, kategori dan keterangan. Saldo diturunkan dari ledger tervalidasi; pembukaan dan pergerakan tidak membuat penjualan atau pembayaran. Satu sesi terbuka per toko; penutupan internal dijelaskan di bawah dan serah-terima belum tersedia. Pemanggil mempertahankan operation ID dan intent untuk retry; intent berbeda ditolak. State, ledger, audit, outbox, receipt dan sequence disimpan atomik di bawah Web Lock. Checkpoint/staging memeriksa histori dan ledger; record generik lama tetap generik.

API ini belum mengimplementasikan izin: `actorId` dan `policyVersion` bukan bukti otorisasi. Integrasi command **dan pembacaan saldo** wajib melalui T-04, termasuk pembatasan staf dan permit; jangan hubungkan ke UI atau tampilkan saldo ke staf. Hitungan fisik dan tutup kas internal dijelaskan di bawah; belum ada server/sync atau backup/restore produksi; pembayaran tunai batch pertama tersedia secara internal seperti dijelaskan di atas. Tes browser lokal memakai Chrome IndexedDB/Web Locks; bukan bukti keamanan, perangkat fisik, restore produksi atau pilot.

### Pembayaran tunai langsung dari draft tersimpan (internal)

`payDraftCash(db, input, metadata)` pada `storage/confirm-first-batch.ts` menerima `orderId`, `expectedDraftRevision`, `mappings` dan `groups` dari rencana stok draft, `expectedSessionRevision`, serta integer `received`. Simpan input dan metadata persis untuk memeriksa hasil tidak diketahui dengan operation ID yang sama. API menyalin intent sebelum Web Lock, memeriksa receipt sebelum guard state, kemudian memvalidasi checkpoint dan membaca ulang draft, sesi asal, mapping, saldo dan revisi di transaksi penulis. Hanya seluruh unit draft yang belum pernah confirmed, total positif dan tunai yang dicakup; nominal kurang, stok kurang atau sumber basi ditolak tanpa efek. Katalog/ketersediaan dan otorisasi belum tersedia: jangan sambungkan command ke UI sebelum prasyaratnya terpenuhi.

Satu receipt `payment.draft-cash` menyimpan batch pertama, job dapur, debit tiap grup, settlement/alokasi, Payment dan job pelanggan, ledger sale sebesar tagihan, revisi sesi, audit, outbox dan sequence. Kembalian adalah uang diterima dikurangi tagihan; saldo kas bertambah sebesar tagihan. Urutan state job adalah dapur lalu pelanggan; job hanya data lokal, tidak membuktikan kertas tercetak. Pembayaran dan penyajian tetap terpisah. Validator commit dan checkpoint/staging memeriksa sumber dan seluruh efek gabungan memakai kontrak baru; kontrak `batch.confirm-first`, `payment.confirmed-cash` dan record generik lama tidak diubah. Konsistensi bukan autentisitas checkpoint. API internal ini tidak membuktikan izin dari `actorId` atau `policyVersion`; T-04 tetap wajib. Batch tambahan, tutup kas, sync, cetak dan restore produksi belum termasuk; non-tunai dan refund served internal dijelaskan di bawah.


### Settlement gratis Rp0 internal

`settleDraftFree` pada `storage/confirm-first-batch.ts` menerima sumber/revisi draft dan stok seperti `confirmFirstBatch`, ditambah `expectedSessionRevision` dan `reason`. `settleConfirmedFirstBatchFree` pada `storage/free-settlement.ts` menerima `orderId`, `expectedBatchRevision`, `expectedSessionRevision` dan `reason`. Alasan wajib teks nonblank maksimal 500 karakter; snapshot settlement dihitung ulang dari draft/batch dengan `source: 'free'` dan total harus tepat Rp0. Simpan ulang input dan metadata yang sama untuk memeriksa hasil tidak diketahui; input disalin sebelum Web Lock dan replay diperiksa sebelum guard state. Operation ID yang sama dengan intent berbeda ditolak.

Draft mengonfirmasi seluruh batch pertama dan mendebit semua unit fisik sekali, termasuk unit gratis, dalam commit bersama settlement, job dapur lalu job pelanggan, audit, outbox, receipt dan sequence. Batch yang sudah confirmed hanya menghasilkan settlement dan job pelanggan: stok, batch, job dapur, penyajian dan sesi tidak berubah, termasuk ketika stok kini nol. Sesi asal harus ada, setoko dan mempunyai revisi yang diharapkan; tidak dibuat atau dipindahkan otomatis. Tidak ada Payment, PlatformReceivable, ledger uang atau perubahan saldo. Settlement tetap terpisah dari penyajian.

Job pelanggan gratis memakai `customer-job` versi 2 yang menyimpan batch, settlement dan alasan tanpa Payment; job tunai versi 1 tetap memerlukan Payment. Receipt gratis menyimpan intent, metadata dan referensi sesi; audit menyimpan alasan, sumber, snapshot dan identitas operasi. Validator commit dan checkpoint/staging merekonstruksi efek dari sumber historis, termasuk mapping/debit draft, menolak efek uang tambahan serta settlement ganda. Kontrak record/receipt lama dan data generik tidak ditebak atau ditulis ulang. Konsistensi checkpoint bukan autentikasi atau restore produksi. Job persisten bukan bukti kertas keluar; jaringan dan cetak tidak dijalankan dalam transaksi.

Kedua command hanya internal dan belum terhubung UI. `actorId`, `policyVersion` dan alasan bukan bukti izin atau approval: **persetujuan owner untuk gratis dan pemeriksaan identitas/izin/perangkat T-04 wajib sebelum integrasi operasional**. Tidak ada approval palsu. Katalog/ketersediaan, auth/permit, batch tambahan, tutup/serah-terima, sync, transport printer dan aktivasi restore tetap di luar cakupan command gratis; non-tunai dan refund served dijelaskan di bawah. Bukti lokal parsial AC-09/10/20/28/30/39/48/151 tidak meluluskan seluruh AC atau pilot.

### Pembayaran non-tunai manual internal

`readPaymentMethods(db, storeId)` mengembalikan konfigurasi dan revisi (`null` bila belum ada); default QRIS, transfer dan e-wallet semuanya nonaktif. Tunai tetap tersedia. `setPaymentMethods(db, {expectedRevision, qris, transfer, ewallet}, metadata)` membuat atau mengganti konfigurasi toko melalui audit, outbox, receipt dan sequence atomik. Perubahan setting hanya untuk owner: T-04 wajib memeriksa identitas, izin dan perangkat sebelum integrasi. `actorId`/`policyVersion` bukan bukti otorisasi.

`payDraftNoncash` di `storage/confirm-first-batch.ts` menerima sumber draft/stok seperti `confirmFirstBatch`; `payConfirmedFirstBatchNoncash` di `storage/noncash-payment.ts` menerima order dan revisi batch. Keduanya juga menerima `expectedSessionRevision`, `expectedMethodsRevision`, `method` (`qris`, `transfer`, `ewallet`), `verified: true`, dan `note` opsional (teks maksimal 500 karakter atau `null`). Total harus positif; satu settlement dan satu Payment dibentuk dari snapshot bersama. Verifikasi adalah pernyataan manusia, bukan bukti otomatis dari screenshot, jaringan atau actor. Pembayaran langsung untuk order platform tetap Payment biasa.

Draft mengonfirmasi batch pertama, mendebit semua unit fisik sekali dan menyimpan job dapur lalu pelanggan dalam commit yang sama. Batch confirmed tidak mendebit lagi dan hanya membuat job pelanggan, termasuk bila stok sekarang nol. Tidak ada ledger uang atau perubahan saldo laci; penyajian terpisah. Konfigurasi, sesi asal, toko dan revisi sumber dibaca ulang dalam transaksi. ## Laporan internal penjualan dan SKU (irisan T-14)

`readInternalSalesReports(db, storeId, filter)` adalah API baca internal, tanpa UI atau otorisasi. T-04 tetap prasyarat akses operasional; actor/policy bukan izin. Filter berupa `{kind:'session', sessionId}` atau `{kind:'calendar', start:'YYYY-MM-DD', end:'YYYY-MM-DD', zone}`; tanggal awal inklusif dan akhir eksklusif dalam zona eksplisit. API mengambil satu checkpoint transaksi baca, memvalidasinya, lalu mengembalikan filter, cakupan, batas sequence, status, alasan incomplete dan laporan. Jika incomplete, `report` bernilai null; checkpoint rusak ditolak.

Cakupan: settlement Payment positif dan gratis batch pertama channel Toko bertipe. Penjualan mengikuti waktu operasi settlement; refund mengikuti waktu dan sesi pelaksanaan, memakai alokasi unit asal termasuk pajak dan layanan. Ringkasan memisahkan bruto, promo, diskon, dasar, pajak, layanan, tagihan, komponen refund, nilai setelah refund, penerimaan neto, jumlah Payment, gratis dan rata-rata Payment. Rincian metode memisahkan penerimaan, refund, koreksi sesi asal dan penyesuaian administratif; kedua kaki klasifikasi berjumlah nol. Rekap SKU memakai nama snapshot, qty terjual/refund/neto, unit bernilai nol atau jumlah gratis dari promo kuantitas dan dasar neto, serta urutan nilai/qty deterministik. Rincian menyertakan ID order, settlement, Payment bila ada, operasi settlement dan operasi kejadian, waktu, sesi dan refund bila ada. Pembatalan, refund due, return, modal dan kas nonpenjualan bukan perpindahan uang penjualan.
