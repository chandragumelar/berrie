# Fondasi aplikasi Berrie

Scaffold belum dapat digunakan untuk transaksi. UI dan data contoh tetap di `../berrie-site/`; integrasi UI mengikuti T-06 setelah fondasi dan izin siap.

Dengan Node 22 dan npm: `npm ci --legacy-peer-deps`, `npm run dev`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. `npm run test:browser` menjalankan tes Chrome lokal melalui Playwright; konfigurasi saat ini memakai Chrome di `/Applications/Google Chrome.app`. `.env.example` tidak berisi rahasia. Lockfile mencatat versi terpasang.

`src/domain` mencakup kalkulasi dan snapshot awal, `src/storage` berisi primitive Dexie berversi, pemeriksaan revisi/urutan dan Web Locks. Ini belum merupakan API transaksi berizin: T-04 harus memvalidasi identitas, kebijakan, permit dan perangkat aktif, dan command bisnis harus memvalidasi seluruh invariants dalam transaksi. Web Locks yang tidak tersedia menyebabkan penolakan, bukan fallback tanpa lock. Checkpoint/staging awal bukan backup terenkripsi atau restore produksi; tidak mengaktifkan database staging. Lihat tasks untuk pekerjaan dan batas yang tersisa.

`stageSnapshot(db, input)` menerima `unknown`, memvalidasi checkpoint schema 1 dan hubungan receipt/state/event/sequence sebelum menulis atomik ke database staging yang masih kosong. Fungsi tidak mengaktifkan staging atau mengubah database sumber. Nilai state baru dapat menggunakan envelope `{ recordType: 'settlement', schemaVersion: 1, settlement }` atau `{ recordType: 'refund-history', schemaVersion: 1, settlement, refunds }`. Gunakan `createSettlementRecord` dan `createRefundHistoryRecord` di `src/domain/business-record.ts`; keduanya memvalidasi dan menyalin input. Commit memvalidasi nilai bertanda sebelum menulis; checkpoint/staging memvalidasi state terkini dan setiap nilai state dalam payload receipt historis. Penanda/versi yang tidak dikenal ditolak. Record generik lama tanpa `recordType` tetap diterima dengan kontrak storage lama, termasuk objek dengan `kind`; isi bisnisnya belum divalidasi. Tidak ada penebakan tipe atau migrasi data lama. Validasi konsistensi bukan bukti autentisitas, otorisasi, atau perlindungan dari manipulasi checkpoint yang terkoordinasi.

`planStockDebits(input)` di `src/domain/stock.ts` menerima `unknown`: `{ rows: [{ rowId, skuId, groupId, qty }], balances: [{ groupId, balance }] }`. ID baris dan grup saldo harus unik dan tidak kosong; SKU boleh berulang. Qty integer 1–999, saldo integer aman ≥0, dan setiap grup baris harus tersedia. Input tidak sah atau overflow melempar error; daftar kosong menghasilkan rencana kosong. Hasil sukses mengurutkan grup dan sumber berdasarkan ID serta memuat kebutuhan, saldo sebelum/sesudah dan sumber; kekurangan menghasilkan `{ ok: false, shortages }` tanpa debit parsial. Contoh dua baris rasa berbeda masing-masing qty1 dalam grup saldo50 menghasilkan kebutuhan2 dan sisa48. Qty mencakup unit gratis/promo; tidak ada konversi, resep atau stok topping.

Ini hanya perhitungan calon konfirmasi, tidak mengubah saldo. Pemanggil kelak wajib memilih hanya unit draft yang belum confirmed dan memvalidasi ulang saldo serta revisi dalam transaksi atomik bersama efek bisnis lain. Fungsi ini tidak membuktikan debit aktual, idempotensi, retry atau integrasi storage.

`planDraftStockDebits(input)` di `src/domain/draft-stock.ts` menerima `unknown`: `{ draft, skuGroups: [{ skuId, groupId }], balances: [{ groupId, balance }] }`. Draft divalidasi dengan `validateDraft`; tiap SKU harus memiliki tepat satu mapping tidak kosong, dan tiap grup yang dipakai harus memiliki saldo. Mapping duplikat, saldo duplikat/hilang atau input tidak sah ditolak. Setiap baris memakai ID item, SKU, grup dan panjang `unitIds`; seluruh unit fisik termasuk gratis/promo dihitung, sedangkan pilihan/topping tidak menambah debit. Agregasi, pemeriksaan saldo, urutan dan hasil `StockPlanResult` didelegasikan ke `planStockDebits`; kekurangan tidak menghasilkan rencana parsial. Contoh qty200 dari saldo1000 menyisakan800, dan dua SKU qty1 dari saldo50 menyisakan48. Input dan hasil terisolasi; fungsi tidak menulis database atau saldo.

Adapter hanya berlaku untuk model draft tersimpan yang belum pernah dikonfirmasi, bukan order campuran confirmed/draft. Mapping dan saldo diberikan pemanggil dan bukan bukti izin atau ketersediaan katalog. Command konfirmasi mendatang tetap wajib membaca dan memvalidasi ulang mapping, saldo dan revisi dalam transaksi; rencana ini bukan debit atau konfirmasi. Tes integrasi create/read memeriksa checkpoint seluruh koleksi tetap identik setelah sukses, kekurangan dan input gagal, tanpa ledger baru. Ini bukti parsial AC-123/151, bukan kelulusan operasional.

## Command draft lokal internal

`createDraft(db, data, metadata)` menyimpan order yang belum pernah dikonfirmasi; `updateDraft(db, data, metadata, expectedRevision)` mengganti draft tersimpan; `readDraft(db, orderId)` mengembalikan draft dan revisinya atau `undefined`. Ini bukan API operasional berizin: `actorId` dan `policyVersion` bukan bukti identitas atau izin, dan command tidak boleh dihubungkan ke UI sebelum T-04 memverifikasi izin, perangkat dan sesi. Command belum memvalidasi katalog, stok, sesi kas, atau izin penjualan.

Data draft berisi UUID order, sesi kas, baris, SKU, unit, pilihan dan topping; identitas antrean/nama, channel, penyajian, catatan, kutipan harga/promo/tarif, dan opsional order asal. Pilihan/topping menyimpan ID dan nama, topping juga harga; `toppingPrice` harus sama dengan jumlah harga topping. Kuantitas adalah panjang `unitIds` per baris (1–999). Draft kosong ditolak saat create maupun update; menghapus seluruh unit melalui lifecycle pembatalan belum dicakup. Harga dan total dihitung domain bersama; tidak ada snapshot settlement, batch, ledger stok/uang atau cetakan yang dibuat.

Saat create, nomor dan `savedAt` dalam data diabaikan: metadata menyediakan `recordedAt` UTC sebagai waktu kejadian dan `storeTimeZone` IANA. Setelah lock diperoleh, command membaca jam perangkat untuk `savedAt` dan waktu pencatatan audit, lalu mengalokasikan nomor per tanggal toko dan epoch dari histori draft bertipe. Pemanggil bertanggung jawab menggunakan waktu kejadian/zona yang benar; sumber waktu tepercaya dan otorisasi belum tersedia. Update memakai UUID, nomor, sesi dan revisi asal dari hasil read; `savedAt` diisi ulang dari jam perangkat saat commit. Baris/unit yang tetap ada mempertahankan ID; ID yang sudah dihapus tidak dipakai ulang. ID eksternal platform ditrim dan diperiksa unik dalam histori draft bertipe per toko/channel/akun. Record generik lama tetap diterima tanpa ditebak menjadi order: nomor atau ID platform tersembunyi di dalamnya tidak dapat direkonsiliasi otomatis; integrasi/migrasi mendatang harus menyelesaikan data tersebut sebelum penggunaan operasional.

Metadata juga berisi `operationId`, `storeId`, `deviceId`, `deviceEpoch`, `localSequence`, `actorId` dan `policyVersion`. Simpan dan gunakan ulang seluruh input serta metadata yang sama saat hasil tidak diketahui: retry identik mengembalikan hasil asal, perubahan apa pun dengan operation ID sama ditolak. Update bersaing pada revisi yang sama menghasilkan satu sukses dan satu konflik. Data disalin sebelum menunggu Web Lock; revisi, tipe target, nomor, audit sebelum/sesudah, state, outbox, receipt dan sequence diperiksa/ditulis atomik. Tidak ada efek jaringan atau printer dalam transaksi.

Envelope `{recordType:'draft', schemaVersion:1, draft}` divalidasi pada commit dan pada setiap state serta receipt checkpoint; staging yang gagal tidak mengubah sumber atau meninggalkan sebagian data. Validasi histori menolak duplikasi identitas dan penggunaan ulang ID yang telah dihapus. Ini belum mengaktifkan staging/restore, membuktikan otorisasi atau mengimplementasikan transisi ke settlement.
